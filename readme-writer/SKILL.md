# README Writer

基于 GitHub/Gitee 高 Star 开源项目 README 的量化分析，为项目生成专业、美观的 README。

## 核心原则

1. **快速理解** - 5 秒内让访客知道这是什么、有什么用
2. **降低门槛** - 清晰的安装步骤和在线 Demo，让用户快速上手
3. **建立信任** - 徽章、截图、许可证、活跃社区，传递项目质量信号

## 工作流

### 1. 收集项目信息

先确认以下信息，缺少的项主动询问用户：

| 必需项 | 可选项 |
|-------|-------|
| 项目名称 | 官网 / 文档地址 |
| 一句话描述（做什么、给谁用） | 在线 Demo 地址 |
| 核心功能列表（3 到 8 个） | 技术栈详情 |
| 安装方式（npm/pip/Docker/源码编译） | 架构设计图 |
| 许可证类型 | 对比竞品 |
| 主要编程语言 | 交流群 / 社区链接 |

如果用户已有项目代码，可通过读取 `package.json`、`setup.py`、`go.mod`、`pom.xml` 等配置文件自动提取信息。

### 2. 判断项目类型并选择侧重

| 类型 | README 侧重 | 典型特征 |
|------|-----------|---------|
| UI 组件库 | 组件列表、在线预览、主题定制 | 提供 Demo 预览页是刚需 |
| 框架 / 引擎 | 架构图、性能对比、快速上手 | 需要解释设计理念和内部原理 |
| CMS / 后台 | 功能截图、技术栈、部署指南 | 截图最能传达产品质感 |
| 工具类 | GIF 演示、使用场景、对比优势 | GIF 比 screenshot 更有说服力 |
| AI / 数据 | 效果截图、模型说明、应用场景 | 强调实际效果而非技术细节 |
| 学习资源 | 目录结构、学习路径、社区链接 | 结构化组织是核心竞争力 |

如果项目同时符合多种类型，选择最主要的一个，并融合其他类型的关键元素。

### 3. 按 README 模板生成

生成 README 时必须包含的章节（按顺序）：

```
1. Logo / Banner（居中）
2. 项目名称 + 一句话描述
3. 徽章行
4. 导航链接（官网 | 文档 | Demo | 常见问题）
5. 功能特性
6. 截图 / GIF
7. 快速开始（前置条件 + 安装 + 使用示例）
8. 贡献指南
9. 致谢 / 赞助商
10. 许可证
```

按项目规模选加的章节：

```
- 目录 (TOC) - 文档超过 150 行时添加
- 技术栈 - 非显而易见的技术选型
- 架构设计 - 复杂系统或多模块项目
- 配置说明 - 有较多配置项时
- 部署指南 - 需要生产环境部署时
- 常见问题 (FAQ) - 有高频问题需提前解答时
- 更新日志 - 用户提供时加入
- 多语言切换 - 面向国际社区时
```

### 4. 视觉设计规则

#### Logo 居中

项目名称和 Logo 必须居中，使用 `<div align="center">` 或 `<p align="center">`：

```markdown
<div align="center">
  <img src="logo地址" alt="Logo" width="100">
  <h1>项目名称</h1>
  <p>一句话描述</p>
</div>
```

#### 徽章

使用 [shields.io](https://shields.io) 生成徽章，精选 3 到 8 个：

| 必加 | 建议加 | 按需加 |
|------|-------|-------|
| 版本号 | 构建状态 | 测试覆盖率 |
| 许可证 | Star 数 | 下载量 |
| 语言 | GVP 认证 | Discord 在线 |

#### 截图与 GIF

- 截图：至少 2 张核心界面，宽屏优先
- GIF：工具类项目强烈建议使用，展示核心交互流程
- 截图上方加一句引导语，如"数据可视化大屏效果"而非直接贴图

#### 代码块

安装和使用步骤必须提供可复制运行的代码块，且标注语言类型。

### 5. 写作风格

#### 一句话描述

长度控制在 **15 到 40 个字**，必须回答两个问题：

- **它是什么**（技术定位）
- **解决什么问题**（核心价值）

好的示例：
- "开源、精美、便捷的数据可视化低代码开发平台"
- "一个基于 Vue3 的企业级 UI 组件库"
- "AI 驱动的智能数据库工具"

差的示例：
- "使用 Rust 编写的跨平台工具"（没说做什么）
- "高性能分布式微服务框架，支持服务发现、配置中心、流量治理、熔断降级、可视化网关..."（太长太碎）

#### 功能特性

使用加粗关键词 + 简短说明的列表格式。避免每个特性超过一行。

```markdown
- **高性能**：基于虚拟 DOM，渲染效率极高
- **组件丰富**：提供 50+ 高质量 UI 组件
- **主题定制**：支持暗黑模式和自定义 CSS 变量
```

功能超过 10 个时，改用表格按分类组织。

#### 语言选择

- 目标用户为国内社区：使用中文
- 目标用户为国际社区：使用英文
- 两者兼顾：中文为主，顶部加语言切换链接

```markdown
简体中文 | [English](README.en.md)
```

## 检查清单

生成 README 后，逐项检查：

- [ ] 一句话描述是否存在且不超过 40 字
- [ ] Logo 和项目名称是否居中
- [ ] 徽章数量是否在 3 到 8 个之间
- [ ] 功能特性是否用加粗列表或表格呈现
- [ ] 是否包含至少 1 张截图或 GIF
- [ ] 安装步骤是否可直接复制运行
- [ ] 是否标注了许可证
- [ ] 文档 / Demo 链接是否有效
- [ ] 总长度是否合理（短项目 < 200 行，复杂项目 < 500 行）

## 常见错误

| 错误 | 后果 | 正确做法 |
|------|------|---------|
| 开头写 FAQ 或常见问题 | 用户还没了解项目就被劝退 | FAQ 放到文档后半部分 |
| 纯技术名词堆砌 | 新用户无法理解 | 加通俗解释 |
| 没有截图 | 无法传达产品质感 | 至少 2 张核心界面截图 |
| 安装缺少前置条件 | 用户安装失败 | 列出环境和版本要求 |
| 没有 Demo 链接 | 用户需克隆代码才能体验 | 提供 Demo 或 Docker 一键部署 |
| 徽章超过 10 个 | 视觉杂乱 | 精选最重要的 |
